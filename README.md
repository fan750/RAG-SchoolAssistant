# 基于 RAG 的校园学习生活信息问答系统

> 软件工程课程设计 · 项目 README（立项草案 v0.1）
> 状态：**待教师审核立项**　|　依据：《软件工程课程设计要求（版本 2）》《课堂形式、内容与要求（户现锋班）》

---

## 1. 项目简介

本系统面向高校校园场景，用检索增强生成（RAG）技术把分散在通知公告、活动推文、讲座预告、场馆与后勤说明中的非结构化信息统一沉淀为可检索的知识库，为师生提供**带原文出处、可追溯、可纠错**的自然语言问答服务。

与通用大模型问答的区别在于三点：

1. **答得准**：答案必须由校内语料检索支撑，无依据时明确拒答，而不是自由发挥；
2. **答得新**：活动、讲座、赛事信息具备时效性，过期内容自动降权或下架；
3. **答得到**：回答附带来源链接与原文片段定位，用户可一键跳转核实。

## 2. 背景与痛点

| 现状问题 | 具体表现 | 本系统的应对 |
| --- | --- | --- |
| 信息孤岛 | 通知在官网、活动在公众号、讲座在学院群、场地在后勤系统 | 多源采集 + 统一知识库 |
| 检索困难 | 关键词搜不到、公告标题不规范、跨文档信息需人工拼合 | 语义检索 + 生成式归纳 |
| 时效混乱 | 往届活动信息与本届混排，用户误信过期内容 | 元数据标注有效期 + 过期下架 |
| 咨询成本高 | 重复性问题占用辅导员、学生会、场馆管理人员大量时间 | 7×24 自助问答 + 未命中转人工 |

## 3. 目标用户与权限

| 角色 | 说明 | 主要权限 |
| --- | --- | --- |
| 访客 | 未登录的校内外人员 | 浏览公开问答、查看公开活动信息 |
| 普通用户（学生 / 教职工） | 经校园统一身份认证登录 | 提问、多轮追问、查看历史、订阅提醒、提交纠错 |
| 活动组织者（社团 / 学院 / 体育部） | 活动与讲座的责任方 | 发布 / 修改本人活动与讲座信息、查看咨询统计 |
| 知识库管理员 | 图书馆或信息中心运营人员 | 文档导入、切片审核、知识条目上下架、纠错处理、质量看板 |
| 系统管理员 | 运维方 | 角色与权限配置、审计日志、模型与索引参数管理 |

权限模型采用 **RBAC + 资源归属**：角色决定功能菜单，资源归属决定数据可见范围（组织者只能改自己发布的活动）。统一身份认证返回的学工号仅用于身份映射，不写入问答日志。

## 4. 典型应用场景

| 场景 | 用户真实问法（示例） | 系统需要的能力 |
| --- | --- | --- |
| 校园马拉松 | "今年校园马拉松什么时候报名？半马和欢乐跑的起跑时间一样吗？" | 赛事规程检索、报名入口定位、时间表抽取 |
| 体育赛事 | "明天下午篮球联赛在哪块场地？下雨有备用场地吗？" | 场馆信息关联、赛程表解析、地图导航 |
| 教授讲座 | "周五下午张教授的报告在哪个楼？需要提前预约吗？" | 讲座预告抽取、预约方式、场地指引 |
| 日常学习生活 | "图书馆暑期开放时间""补办校园卡要带什么材料" | 规章制度问答、办事流程归纳 |

场景的共同特征是**信息分散、更新频繁、用户只想知道"在哪、什么时候、怎么参加"**，这正是 RAG 相比关键词搜索的优势区间。

## 5. 系统范围

**本期做：**

- 多源语料采集与文档解析（PDF / Word / 网页 / 公众号图文导出）
- 知识切片、向量化、元数据（来源、发布时间、有效期、所属场景）管理
- 检索 + 重排 + 生成 + 引用回溯的问答链路
- 多轮追问、场景筛选、未命中转人工、答案反馈与纠错
- 活动 / 讲座信息的发布、审核与订阅提醒
- 运营看板与检索质量评测

**本期不做（明确排除，避免范围膨胀）：**

- 不做通用校园助手（课表、成绩、一卡通余额等业务系统数据直连）
- 不做活动在线报名与支付（仅提供报名入口跳转）
- 不自研大模型与向量数据库，均采用成熟组件集成
- 不做移动端原生 App，本期为响应式 Web

## 6. 功能规划与用例规模

规划 **22 个用例**（含 4 个非功能用例），分三个增量交付。

| 模块 | 用例 | 编号 |
| --- | --- | --- |
| 账号与权限（4） | 统一身份认证登录、访客浏览、角色权限管理、问答历史管理 | UC-01 ~ UC-04 |
| 知识采集与治理（6） | 活动/讲座发布、信息纠错提交、文档批量导入、文档解析与切片、知识条目审核发布、过期内容下架 | UC-05 ~ UC-10 |
| 智能问答（6） | 自然语言提问、多轮澄清、引用来源与原文定位、场景筛选、未命中转人工、答案反馈 | UC-11 ~ UC-16 |
| 活动服务（3） | 赛程与报名信息查询、场地地图导航、订阅提醒推送 | UC-17 ~ UC-19 |
| 运营与评测（3） | 问答质量看板、评测集管理、敏感内容审核 | UC-20 ~ UC-22 |
| 非功能（4） | 响应时延、答案可溯源与拒答、并发与可用性、个人信息保护 | UNF-01 ~ UNF-04 |

### 6.1 非功能需求（初稿）

| 编号 | 指标 | 验收方式 |
| --- | --- | --- |
| UNF-01 | 单轮问答 P95 响应时间 ≤ 5 s（不含大模型排队） | 压测脚本 + 日志统计 |
| UNF-02 | 每个校内事实陈述均有支持它的引用。部分有依据时回答可确认事项，并说明其余事项暂未确认。各事项均无有效证据且无已知待核实状态时拒答并提供求助入口 | 固定离线题集人工核对 |
| UNF-03 | 活动发布高峰期支持 100 并发问答，服务可用性 ≥ 99% | 并发压测 + 监控看板 |
| UNF-04 | 问答日志不含学工号、手机号等个人敏感信息；语料访问受角色约束 | 日志审计 + 权限用例验证 |

### 6.2 主要分析类（规划 ≥15，最终以分析模型为准）

用户、角色、权限、身份映射、知识文档、文档切片、知识条目、活动、讲座、赛事、场地、问答会话、问题、答案、引用片段、用户反馈、纠错单、订阅、提醒、评测集、审计日志。

## 7. 技术方案概览（初步选型）

```
Web 前端（Vue 3 + TypeScript）
        │  HTTPS / REST
API 服务（FastAPI，含鉴权与限流）
        │
问答编排：问题改写 → 混合检索（向量 + 关键词）→ 重排 → 生成 → 引用校验 / 拒答
        │
PostgreSQL + pgvector（知识切片、元数据、业务数据）  对象存储（原始文档）
        ↑
采集管道：公告爬取 / 文档上传 / 组织者录入 → 解析 → 切片 → 审核 → 入库
        │
外部集成：校园统一身份认证（OAuth2 / CAS）、地图服务（增量 2）、消息推送（增量 2）
```

选型原则是**降低运维面**：向量检索直接用 pgvector 而非独立向量库，减少一套中间件；大模型与 Embedding 通过 API 调用，密钥存于环境变量 / GitHub Secrets，严禁进入提示词与仓库。最终技术决策在设计阶段以 ADR 形式定稿。

## 8. 过程模型选型论证

| 候选模型 | 与本项目的匹配度 | 结论 |
| --- | --- | --- |
| 瀑布 | 需求需真人调研后才稳定，语料与算法效果又必须靠试跑才能知道，一次性冻结需求风险过高 | 不采用 |
| 螺旋 | 风险驱动的迭代思路契合"RAG 效果不确定"这一特点，但完整螺旋的正式风险分析与原型轮次对 1 学分、8 次课的课时而言过重 | 借鉴其风险驱动思想，不整体采用 |
| RUP / UP | 用例驱动、以架构为中心、迭代增量与课程检查点高度一致；但四阶段的完整制品链（业务建模、多套视图）对本规模偏重 | 借鉴用例驱动与阶段裁剪，不整体采用 |
| 敏捷 Scrum | 2 周迭代、可运行增量、每轮回顾，天然匹配"课次即检查点"的节奏；但纯敏捷弱化文档，与课程"文档链可追溯"要求冲突 | 采用，但做文档强化 |
| **增量式 + 轻量 Scrum（选定）** | 三个增量可以各自独立演示；每轮迭代产出可运行版本并回顾；关键规约（SRS、设计规约）在迭代前冻结基线 | **采用** |

选型理由展开：

1. **需求可分块，适合增量**：知识库问答（增量 1）、活动服务（增量 2）、运营质量（增量 3）三条主线耦合度低，可独立交付、独立演示，正好对应课程要求的 ≥3 个可交付增量与 v0.1 / v0.2 / v0.3 三个 Release。
2. **效果不确定性高，需要早试跑**：用真实语料验证检索质量、切片策略和证据不足时的回答。尽早跑通采集到问答，才能在迭代中发现并修复问题。
3. **干系人反馈周期短**：教师点评、组间互评每周一次，本身就是天然的 Sprint Review，采用 2 周迭代可把课堂点评直接转化为下一轮待办。
4. **文档与流程可控**：在 Scrum 之上保留需求基线、变更申请-评审-批准、正式评审单等重型实践，满足课程的文档链与"人守关卡"要求。

迭代安排：**迭代 1**（第 9–11 周，完成调研、SRS、模型骨架与问答链路原型）；**迭代 2**（第 12–14 周，分析建模定稿、概要设计、活动场景落地）；**迭代 3**（第 15–16 周及课后，详细设计、编码测试、部署与答辩准备），每轮输出迭代计划与回顾报告。

## 11. GitHub 工程规范

- **分支**：`main` 开启保护，禁止直推；功能走 `feat/<模块>-<简述>`，修复走 `fix/<编号>`，每张图、每份规约单独 PR。
- **PR**：至少 1 人评审后合并，PR 描述必须关联 Issue 编号；合并前 CI 必须绿灯。
- **Issue**：需求、缺陷、变更一律建 Issue；需求变更走"申请 → 评审 → 批准 → 关闭"并留痕。
- **CI**：GitHub Actions 在 push / PR 时执行 Lint + 单元测试 + 文档链接检查，红灯禁止合并。
- **里程碑与发布**：每个增量一个 Milestone，对应 `v0.1` / `v0.2` / `v0.3` Release，答辩前发布 `v1.0`。
- **提交纪律**：按人统计提交分布，禁止期末集中打包提交；每人至少 10 个被合并的 PR、至少主讲 1 次课堂讲解。

| 编号 | 风险 | 影响 | 应对措施 | 责任人 |
| --- | --- | --- | --- | --- |

| R3 | 信息时效性失控 | 回答过期活动 | 元数据有效期字段；到期自动降权；过期下架用例 | 知识库管理员 |
| R4 | 身份与隐私合规 | 安全事故红线 | 统一认证只做映射；日志脱敏；密钥入 Secrets | 全体 / AI 使用负责人 |
